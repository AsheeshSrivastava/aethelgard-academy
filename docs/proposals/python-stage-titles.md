# Proposal: Python Stage Titles

- **Status:** Approved by the owner on 2026-10-31. Applied in `curriculum/python/stages.json`; the roadmap file is unchanged.
- **Date:** 2026-10-31
- **Why:** the Python Subject Roadmap v3 stage headings have no titles, so the course map shows "Stage 3". The Backend and AI Engineering roadmaps already have titles.
- **Sources:** the unit titles in each stage, and `docs/architecture/02-operational-narrative-spine-78-units.md`.

Titles name the capability, not the story, so the same title still works if the narrative changes. This matches the style of the other two roadmaps.

| Stage | Proposed title | Reason |
| --- | --- | --- |
| 0 | Running your first program | Covers a first program, execution order, and tool help versus your own reasoning. |
| 1 | Values, text and collections | Numbers, text, names, sequences and mappings are the data a program works with. |
| 2 | Conditions, loops and control flow | Conditions, iteration and comprehensions all decide which code runs, and when. |
| 3 | Functions and decomposition | Moves from calling functions to designing them and splitting a requirement. |
| 4 | Errors, validation and failure contracts | All four units are about failing clearly instead of silently. |
| 5 | Modules, packages and project structure | Splitting code across files, up to reading a small real application. |
| 6 | Classes and object design | Goes from instances and state through to composition and responsibility. |
| 7 | Iterators, decorators and type contracts | Groups the advanced language tools: lazy iteration, wrappers, resources and types. |
| 8 | Files, data and external services | Files, structured data, configuration, command lines and HTTP are the program's edges. |
| 9 | Testing, debugging and runtime evidence | Each unit gathers proof of how the code actually behaves. |
| 10 | Environments, packaging and quality gates | Covers what it takes for code to run somewhere other than your machine. |
| 11 | Concurrency and async | Mental model, threads, processes, async tracing and async failures. |
| 12 | Working in existing codebases | Navigating, learning from documentation, changing safely and refactoring. |
| 13 | Owning a Python subsystem | The capstone: building a subsystem and owning AI-assisted work. |
